# TDD Assessment — QuickRecorder

Audit date: 2026-05-01
Plan: `docs/plans/2026-05-01-001-refactor-bau-design-criteria-assessment-plan.md` (U3)
Scope: Test coverage and TDD-as-workflow signal across the QuickRecorder/ source tree.

## Methodology

This audit produces a coverage map of every non-trivial Swift source file (>100 LOC) under `QuickRecorder/` against the test files under `QuickRecorderTests/` and `QuickRecorderUITests/`. It layers onto `QuickRecorderTests/TEST_IMPROVEMENTS.md`, `QuickRecorderTests/RUN_TESTS.md`, and `scripts/TEST_EVALUATION_REPORT.md` rather than re-deriving their findings (mock gaps, hardware dependencies, state-cleanup defects). Coverage labels are: **Covered** = a dedicated `*Tests.swift` file targets the source symbol(s); **Partial** = some symbols are tested but large surface remains untested; **None** = no test references the file. Workflow signal comes from `git log --since='2026-02-01' --stat` plus a wider window (Nov-2025 onward) since no source-file commits appear in the narrower window. All paths are repo-relative.

## Findings

### F-tdd-1. Entire `QuickRecorder/ViewModel/` directory has no test coverage

- Location: `QuickRecorder/ViewModel/*.swift` (14 files, ~3,890 LOC of view-model code)
- Severity: High
- Effort: L
- Status: confirmed
- Evidence: Coverage map rows for `QmaPlayer.swift` (678), `AreaSelector.swift` (549), `ContentView.swift` (424), `AppSelector.swift` (363), `WinSelector.swift` (361), `SettingsView.swift` (348), `CameraOverlayer.swift` (245), `StatusBar.swift` (240), `ScreenSelector.swift` (230), `ContentViewNew.swift` (223), `PreviewView.swift` (193), `VideoEditor.swift` (161), `iDeviceSelector.swift` (139), plus three trivial files. `grep -l` against `QuickRecorderTests/*.swift` returns zero matches for any ViewModel symbol. UI tests in `QuickRecorderUITests/` are launch-smoke only.
- Why it matters: ViewModels host the user-visible logic (area selection geometry, settings persistence, QMA player state machine, status-bar coordination). With zero tests, every refactor of `SCContext`/`RecordEngine` (already proposed in U1 SOLID) lacks a regression net at the consumer layer. `QmaPlayer.swift` at 678 LOC is the second-largest file in the repo and ships entirely unverified.
- Recommendation: Stand up at least one test per ViewModel >300 LOC, prioritized `QmaPlayer.swift` -> `AreaSelector.swift` -> `SettingsView.swift`. Pair with the dependency-injection pattern already drafted in `QuickRecorderTests/TEST_IMPROVEMENTS.md` so ViewModels can be exercised without a live `SCContext.shared`.
- Follow-up plan: `feat: backfill unit tests for ViewModel layer (QmaPlayer, AreaSelector, SettingsView first)`

### F-tdd-2. `QuickRecorder/Supports/AppleScript.swift` has no tests despite being an OWASP-flagged surface

- Location: `QuickRecorder/Supports/AppleScript.swift` (233 LOC)
- Severity: High
- Effort: M
- Status: confirmed
- Evidence: Coverage map row — no test file references this module. The plan's U2 (OWASP) calls AppleScript an injection-risk surface; absent tests mean any hardening change cannot be regression-checked.
- Why it matters: AppleScript execution is one of the few code paths in this app that constructs and runs interpreted code at runtime. Untested + security-sensitive is the worst combination on the matrix. A correctness regression here is an accessibility/permission incident, not a UI papercut.
- Recommendation: Add a focused test file `AppleScriptTests.swift` covering: input sanitization for any user-supplied string interpolated into AppleScript source, error propagation when script execution is denied, and behavior when the target app is absent. Coordinate with whatever U2 produces so the tests assert the intended security invariants rather than the current ones.
- Follow-up plan: `feat: add AppleScript surface tests covering injection and permission error paths` (sequence after U2 OWASP findings)

### F-tdd-3. `QuickRecorder/Supports/WindowHighlighter.swift` (330 LOC) and `Supports/GroupForm.swift` (266 LOC) untested

- Location: `QuickRecorder/Supports/WindowHighlighter.swift`, `QuickRecorder/Supports/GroupForm.swift`
- Severity: Medium
- Effort: M
- Status: confirmed
- Evidence: Coverage map — neither file is referenced by any test. Both exceed the >100 LOC threshold and are non-trivial helper modules, not simple extensions.
- Why it matters: `WindowHighlighter` is invoked during area/window selection; visual regressions are user-visible. `GroupForm` is a reusable SwiftUI form component — drift here propagates across every settings/selector screen that consumes it.
- Recommendation: Add light-weight unit tests for the pure logic in each (geometry calculations, form binding helpers). Skip pixel-level NSView testing — out of scope for unit suite. Defer SwiftUI rendering tests to a separate UI-test backfill.
- Follow-up plan: `feat: add unit tests for Supports/WindowHighlighter and Supports/GroupForm pure logic`

### F-tdd-4. `RecordEngineTests` mocks return nil, leaving prep-record tests as compile-checks rather than behavior assertions

- Location: `QuickRecorder/RecordEngine.swift` x `QuickRecorderTests/RecordEngineTests.swift`
- Severity: Medium
- Effort: S
- Status: confirmed
- Evidence: `scripts/TEST_EVALUATION_REPORT.md` flags `createMockDisplay() -> SCDisplay? { return nil }` (lines 298-312 of `RecordEngineTests.swift` per that report). `QuickRecorderTests/TEST_IMPROVEMENTS.md` lays out the fix (proper `MockSCDisplay`, `MockSCWindow`, `MockSCRunningApplication` subclasses) but those mocks are not yet in `TestHelpers.swift`. The 13 RecordEngine tests therefore cannot meaningfully assert post-prepRecord state for the success paths.
- Why it matters: `RecordEngine.swift` is the second-largest file (774 LOC) and the orchestration core. Tests that look like coverage but execute only error paths are worse than no tests — they create false confidence that blocks a U1-driven SOLID refactor.
- Recommendation: Land the mocks already drafted in `TEST_IMPROVEMENTS.md` into `TestHelpers.swift`, then have each `prepRecord` test assert the resulting `SCContext.streamType`, `SCContext.stream`, and `vW` state.
- Follow-up plan: `fix: implement SCDisplay/SCWindow/SCRunningApplication test mocks per TEST_IMPROVEMENTS.md`

### F-tdd-5. `SCContext` tests miss the stream lifecycle and permission paths

- Location: `QuickRecorder/SCContext.swift` x `QuickRecorderTests/SCContextTests.swift`
- Severity: Medium
- Effort: M
- Status: confirmed
- Evidence: `SCContext.swift` is 839 LOC; `SCContextTests.swift` exercises ~5 method families (file path, audio settings, background color, pause toggle, time adjust). Stream start/stop, content filter construction, permission acquisition flow, and the static state surface (`SCContext.stream`, `SCContext.vW`, `SCContext.audioFile`, `SCContext.startTime`, etc.) are not asserted. `TEST_IMPROVEMENTS.md` Fix 4 explicitly notes that tests do not even reset this static state in `tearDown`, so cross-test contamination is also a risk.
- Why it matters: This is the god-object that U1 SOLID will likely propose splitting. Refactoring it without lifecycle tests is uncomfortable; adding tests now de-risks the refactor.
- Recommendation: Extend `SCContextTests.swift` with: (a) `tearDown` that resets every mutable static (per Fix 4 in TEST_IMPROVEMENTS), (b) lifecycle tests for stream type transitions, (c) one test per permission outcome (granted / denied / restricted).
- Follow-up plan: `feat: extend SCContextTests with lifecycle, permission, and static-state-cleanup coverage`

### F-tdd-6. No CI executes the test suite; TDD-workflow signal is structural only

- Location: repository root (no `.github/workflows/` test job)
- Severity: Medium
- Effort: S
- Status: confirmed
- Evidence: Commit `b9e0875` (2025-12-28) added `.github/workflows/tests.yml` (109 lines per the commit's `--stat`); commit `4dc1d1a` (same day) removed it as part of "Match original lihaoyun6/QuickRecorder structure". Subsequent commits do not restore it. `git log --since='2026-02-01'` shows zero source/test commits, so there is no recent green/red signal to inspect either.
- Why it matters: TDD is a workflow criterion (per the plan's U3 approach). Without CI, "tests exist" is a one-time fact, not a discipline. Future contributions can land without exercising the suite at all.
- Recommendation: Restore a minimal CI job that runs `xcodebuild test -scheme QuickRecorder -destination 'platform=macOS'` on PRs. Even a single GitHub Actions runner gating merges converts the existing 100+ tests from a static asset into an active gate.
- Follow-up plan: `chore: restore GitHub Actions test workflow for QuickRecorder scheme`

### F-tdd-7. `QuickRecorderApp.swift` lifecycle and AppDelegate wiring untested

- Location: `QuickRecorder/QuickRecorderApp.swift` (687 LOC)
- Severity: Medium
- Effort: M
- Status: confirmed
- Evidence: `UtilityTests.swift` covers only `String`/`NSImage`/`CMSampleBuffer` extensions and `FixedLengthArray` that happen to live inside `QuickRecorderApp.swift`. `grep` confirms those extensions are defined here, but the `@main` `App` body, `AppDelegate` callbacks, hotkey registration, status-bar setup, and notification-permission glue have no coverage.
- Why it matters: `QuickRecorderApp.swift` is the third-largest file in the repo and the single point where the app wires together every subsystem. Bugs here surface as "the app won't launch" or "shortcuts stopped working" — exactly the regressions UI launch-smoke tests don't catch.
- Recommendation: Pull the non-`@main` glue (hotkey registration, notification-permission requestor, settings observers) into testable helpers, then unit-test those helpers. SwiftUI `App` body itself does not need a unit test.
- Follow-up plan: `refactor+feat: extract testable helpers from QuickRecorderApp.swift and add coverage` (sequence after U1 SOLID names extraction boundaries)

### F-tdd-8. UI launch-smoke tests are minimal and non-functional

- Location: `QuickRecorderUITests/QuickRecorderUITests.swift` (41 LOC), `QuickRecorderUITests/QuickRecorderUITestsLaunchTests.swift` (33 LOC)
- Severity: Low
- Effort: M
- Status: confirmed
- Evidence: 74 LOC total across two files; effectively launch-smoke + a placeholder example (the standard Xcode-template UI test scaffolding).
- Why it matters: Real user flows (start recording -> stop recording -> verify file written; toggle settings -> verify persistence) are exactly what UI tests should pin. Their absence means coverage of the integration seam between ViewModel and SCContext is zero.
- Recommendation: After the higher-severity ViewModel unit-test gap is addressed, add 2-3 end-to-end UI tests for the primary recording flows. Lower priority because UI tests are slow and the unit-test gap dominates risk.
- Follow-up plan: `feat: add primary-flow UI tests (start/stop recording, settings persistence)` — after F-tdd-1 lands
