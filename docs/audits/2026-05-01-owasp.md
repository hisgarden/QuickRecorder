## Findings

### F-owasp-1. Apple App-Specific Password committed and pushed in `scripts/STAPLING_GUIDE.md`

- Location: `scripts/STAPLING_GUIDE.md` (commits `e83c933`, `faa9e32`, `e511f04`; reachable from `origin/main` HEAD `380d07e`). Co-located in the same blob: Apple ID email `<REDACTED-APPLE-ID-EMAIL>` and Apple Team ID `<REDACTED-APPLE-TEAM-ID>`.
- OWASP category: A02 Cryptographic Failures (credential storage) / A05 Security Misconfiguration (secret in tracked documentation)
- Severity: **Critical**
- Effort:   M (rotate now is S; full history rewrite + force-push coordination is M)
- Status:   confirmed
- Evidence: `git log --all --oneline -S '<REDACTED-APPLE-ASP>'` returned three commits, all touching `scripts/STAPLING_GUIDE.md`. The exposing block is in a "Troubleshooting" example that uses real credentials instead of placeholders:

  ```
  xcrun notarytool history \
      --apple-id <REDACTED-APPLE-ID-EMAIL> \
      --password <REDACTED-APPLE-ASP> \
      --team-id <REDACTED-APPLE-TEAM-ID>
  ```

  `git fetch origin main` followed by `git show origin/main:scripts/STAPLING_GUIDE.md | grep -c '<REDACTED-APPLE-ASP>'` returned `0` only against the **remote** blob's *placeholder* lines — but `git log origin/main --oneline -S '<REDACTED-APPLE-ASP>'` returned commit `e83c933` as reachable from `origin/main`, meaning the value is in the public history even if the current HEAD's blob has been rewritten to a placeholder. (Conservative read: assume the secret is publicly exposed.)
- Why it matters: Apple App-Specific Passwords are a full notarization credential. With Apple ID email + Team ID + ASP, an attacker can submit notarization requests as the maintainer, abuse Apple's notarization service, and — depending on Apple's account-level controls — pivot to other Apple ID surfaces. Because the credential is on GitHub's public main branch and reachable from history, the exposure window is already open: secret-scanning bots and forks may already have copies. The credential must be treated as compromised.
- Recommendation:
  1. **Rotate the Apple App-Specific Password immediately** at <https://appleid.apple.com/account/manage> — revoke `<REDACTED-APPLE-ASP>` and generate a new one. Do this BEFORE any history rewrite, because rewriting first only narrows the window for fresh attackers, it does not retroactively un-leak.
  2. After rotation, treat history rewrite as defense-in-depth, not the fix. Decide between `git filter-repo`/`git filter-branch` + force-push to `origin/main` (coordinated with any collaborators) vs. accepting public exposure of a now-revoked credential. Either is acceptable post-rotation; rewriting is cleaner long-term.
  3. Audit Apple's notarization submission history (`xcrun notarytool history --apple-id <REDACTED-APPLE-ID-EMAIL> --keychain-profile <new-profile>`) for any submissions the maintainer did not initiate.
  4. Replace the inline secret in `scripts/STAPLING_GUIDE.md` with a placeholder pattern (e.g., `xxxx-xxxx-xxxx-xxxx`) or, better, a reference to the Keychain workflow already documented elsewhere in `scripts/`.
  5. Out of scope for OWASP, but worth flagging: the local `.env` also contains a live GitHub PAT (`<REDACTED-GH-PAT>`) and the same Apple ASP. The GitHub token is not in git history (verified) but is on disk at mode `0644`. Rotate the GitHub PAT too, and consider tightening `.env` to `0600`.
- Follow-up plan: `fix: rotate exposed Apple notarization credential and scrub scripts/STAPLING_GUIDE.md from git history` — the rotation must be the user's decision and action; this audit cannot perform it. Audit U2 should be re-run after rotation completes to cover the remaining OWASP lenses.
