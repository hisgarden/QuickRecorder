# SOLID Assessment — QuickRecorder (2026-05-01)

## Methodology

This audit was produced by reading the eight largest/most-coupled Swift sources end-to-end and grouping each file's responsibilities into cohesive clusters. Files reviewed:

- `QuickRecorder/SCContext.swift` (839 lines)
- `QuickRecorder/RecordEngine.swift` (774 lines)
- `QuickRecorder/QuickRecorderApp.swift` (687 lines)
- `QuickRecorder/ViewModel/QmaPlayer.swift` (678 lines)
- `QuickRecorder/ViewModel/AreaSelector.swift` (549 lines)
- `QuickRecorder/ViewModel/ContentView.swift` (424 lines)
- `QuickRecorder/ViewModel/SettingsView.swift` (348 lines)
- `QuickRecorder/AVContext.swift` (154 lines)

The rubric is the canonical SOLID principles. Severity follows the per-criterion calibration in the parent plan: Critical for god-objects in hot paths; High for SRP breaches in 500+ LOC files mixing UI/business/IO; Medium for OCP/DIP friction; Low for cosmetic. LSP/ISP are spot-checked only — none of the read code uses class hierarchies or cross-module protocols where those principles would dominate.

A consistent structural pattern emerged across every reviewed file: the codebase uses `SCContext` (all-static) plus the `AppDelegate` singleton as a global mutable bus, and almost every responsibility — UI, capture orchestration, AV writer setup, audio file I/O, notifications, alerts, file format conversion, AppleScript-style global window manipulation — reaches into both. Most findings below are different facets of that same root issue.

## Findings

### F-solid-1. SCContext is a god-object holding capture state, file I/O, permissions, audio mixing, and notifications

- Location: `QuickRecorder/SCContext.swift:17-839` (entire `class SCContext`)
- Severity: Critical
- Effort:   L
- Status:   confirmed
- Evidence: One `class SCContext` declares 28 static stored properties (lines 18-53) spanning unrelated concerns — capture session state (`stream`, `filter`, `streamType`, `screen`, `window`, `application`, `availableContent`), AV writer state (`vW`, `vwInput`, `awInput`, `micInput`), file paths (`filePath`, `filePath1`, `filePath2`), audio engines (`audioEngine`, `AECEngine`), pause/resume bookkeeping (`isPaused`, `isResume`, `lastPTS`, `timeOffset`, `startTime`, `timePassed`), camera sessions (`captureSession`, `previewSession`), trim list, frame cache, magnifier flag, screen-area rect, and a wallpaper background color. Static methods cover at least eight distinct domains: `updateAvailableContent…`/`getApps`/`getWindows` (content discovery, lines 55-148), `getAppIcon`/`getScreenWithMouse`/`getSCDisplayWithMouse` (UI/display lookup, 150-178), `getFilePath`/`updateAudioSettings`/`getBackgroundColor` (config derivation, 180-225), `performMicCheck`/`requestPermissions`/`requestCameraPermission` (TCC permission UX, 227-274), `getRecordingSize`/`getRecordingLength`/`isCameraRunning`/`pauseRecording`/`stopRecording` (recording state machine, 289-477), `showPreview`/`m4a2mp3`/`trimVideo` (post-processing UI + encode, 479-514), `getCameras`/`getMicrophone`/`getiDevice`/`getCurrentMic`/`getSampleRate`/`getDefaultSampleRate` (AV device discovery, 516-683), `adjustTime`/`showNotification`/`mixAudioTracks` (sample timing math + UNUserNotification + AVAssetExportSession orchestration, 685-838). `stopRecording` alone (lines 329-477) reaches into `AppDelegate.shared`, `mousePointer`, `screenMagnifier`, `controlPanel`, `camWindow`, `deviceWindow`, `previewWindow`, `SleepPreventer.shared`, `AudioRecorder.shared`, `qmaPackageHandle`, `AudioPlayerManager`, and `VideoTrimmerView`.
- Why it matters: Single-Responsibility Principle. This is the single highest-leverage SRP violation in the repo: every recording feature, every UI surface, and every test must transit this class, and every change risks unrelated regressions because state is shared via static globals. It also breaks DIP — every consumer (RecordEngine, AVContext, QmaPlayer, ContentView) depends concretely on `SCContext.*` rather than on injected protocols.
- Recommendation: Carve `SCContext` into ~6 collaborator types behind protocols, landed incrementally:
  1. `CaptureContentDiscovery` — `availableContent`, `updateAvailableContent`, `getApps`, `getWindows`, `getSelfWindows`, `getSCDisplayWithMouse`.
  2. `RecordingStateStore` — `streamType`, `stream`, `screen`, `window`, `application`, `screenArea`, `isPaused`, `isResume`, `startTime`, `timePassed`, `lastPTS`, `timeOffset`, plus `pauseRecording`.
  3. `AssetWriterCoordinator` — `vW`, `vwInput`, `awInput`, `micInput`, `audioFile`, `audioFile2`, `filePath{,1,2}`, `updateAudioSettings`.
  4. `PermissionsCoordinator` — `performMicCheck`, `requestPermissions`, `requestCameraPermission`.
  5. `PostProcessingService` — `mixAudioTracks`, `m4a2mp3`, `trimVideo`, `showPreview`, `showNotification`.
  6. `AVDeviceDirectory` — `getCameras`, `getMicrophone`, `getiDevice`, `getCurrentMic`, `getSampleRate`, `getDefaultSampleRate`.
  Each lands as its own PR; `SCContext` remains as a thin facade until callers migrate.
- Follow-up plan: refactor: split SCContext.swift into capture / state / writer / permissions / post-processing / device-directory collaborators

### F-solid-2. AppDelegate is a god-object owning lifecycle, capture pipeline, AV delegate, mouse monitors, settings, and window choreography

- Location: `QuickRecorder/QuickRecorderApp.swift:108-418` (`class AppDelegate`); extended further in `QuickRecorder/RecordEngine.swift:16-632`, `QuickRecorder/AVContext.swift:12-50`, `QuickRecorder/ViewModel/ContentView.swift:342-408`, `QuickRecorder/ViewModel/SettingsView.swift:337-348`
- Severity: Critical
- Effort:   L
- Status:   confirmed
- Evidence: `AppDelegate` declares conformance to four protocols simultaneously — `NSApplicationDelegate, SCStreamDelegate, SCStreamOutput, AVCaptureVideoDataOutputSampleBufferDelegate` (line 108) — and is split across five files via `extension AppDelegate`. It carries 25+ `@AppStorage` properties duplicating settings already used in `SettingsView` (lines 117-148), it owns the global mouse monitor (`registerGlobalMouseMonitor`, `mousePointerReLocation`, `screenMagnifierReLocation`, lines 150-187), and it implements the entire ScreenCaptureKit hot-path: `prepRecord` (RecordEngine.swift:17-138, ~120 LOC of filter/stream-config branching), `record` (RecordEngine.swift:140-303), `prepareAudioRecording` (305-342), `initVideo` (362-436), `startMicRecording` (438-468), `stream(_:didOutputSampleBuffer:of:)` (489-622, the per-frame callback). It also implements the camera AV pipeline (`recordingCamera`, `closeCamera` in AVContext.swift:13-41), opens settings panels (SettingsView.swift:339-347), and creates floating area-selector / countdown / generic windows (ContentView.swift:343-407). Because `AppDelegate.shared` is reachable from every SwiftUI view and from `SCContext`, it is mutually entangled with finding F-solid-1.
- Why it matters: SRP and DIP. The class has at least 6 reasons to change (UI, capture filter setup, asset-writer setup, AV delegate callbacks, mouse-event handling, settings persistence). Splitting it across multiple `extension` files visually hides the size but does not reduce coupling. Every test for any part of the recording pipeline must instantiate (or mock) the entire app delegate.
- Recommendation: Extract three collaborators owned by `AppDelegate` rather than mixed into it:
  1. `RecordingPipelineCoordinator` — owns `prepRecord`, `record`, `initVideo`, `prepareAudioRecording`, `startMicRecording`, the SCStream delegate methods, and the per-frame `stream(_:didOutputSampleBuffer:of:)` callback. This is the natural home for the contents of `RecordEngine.swift`.
  2. `MouseAndMagnifierMonitor` — owns `mousePointerReLocation`, `screenMagnifierReLocation`, `registerGlobalMouseMonitor`, `stopGlobalMouseMonitor`.
  3. `WindowDirector` — owns `showAreaSelector`, `createCountdownPanel`, `createNewWindow`, `openSettingPanel`, `closeAllWindow`, `closeMainWindow`. Currently these are scattered across `ContentView.swift`, `QuickRecorderApp.swift`, and free functions.
  Settings storage should move to a single `RecordingSettings` observable; the duplicate `@AppStorage` declarations across `AppDelegate` and per-view `SettingsView` subviews (e.g., `RecorderView` lines 98-108 vs `AppDelegate` lines 117-148) are a maintenance trap.
- Follow-up plan: refactor: extract RecordingPipelineCoordinator + MouseAndMagnifierMonitor + WindowDirector from AppDelegate

### F-solid-3. RecordEngine.swift mixes filter construction, stream config, asset-writer construction, audio routing, frame-callback dispatch, and HEIF export

- Location: `QuickRecorder/RecordEngine.swift:16-632` (extensions on `AppDelegate`); plus the inline `class AudioRecorder` at 634-697 and three free `extension`s at 345-359 and 701-774
- Severity: High
- Effort:   L
- Status:   confirmed
- Evidence: The file is structured as one giant `extension AppDelegate` and intermixes: stream-type dispatch via string switch (lines 18-26), filter assembly with deep wallpaper/dock/finder special-casing (lines 60-138), `SCStreamConfiguration` setup with HDR / non-HDR branching (lines 147-220), source-rect math for screen-area mode (242-255), VideoToolbox H.264 capability probing + interactive alert (258-283), asset-writer initialization for video (`initVideo` 362-436) and audio (`prepareAudioRecording` 305-342), microphone-input wiring across two engines (`startMicRecording` 438-468), the per-frame dispatch callback with HEIF/PNG snapshot saving inlined (`stream(_:didOutputSampleBuffer:of:)` 489-622, with a 70-line nested branch that imports `CIContext` and writes PNG/HEIF), and PTS bookkeeping (547-600). A separate `class AudioRecorder` is declared in the same file (634-697) for non-default mic devices. The same file then defines `extension CMSampleBuffer` (701-723) and `extension AVAudioPCMBuffer` (726-774) for buffer conversion utilities.
- Why it matters: SRP and OCP. Each new capture mode, encoder, or output format requires editing one of the long ladders (e.g., the `switch type` on line 18, the `switch fileEnding` on lines 309/367, the `switch outputType` on line 559). The per-frame callback is the hottest code path in the app and is currently mixed with snapshot-saving I/O and presenter-overlay UI signaling — meaning a regression in still-frame export can deadlock recording.
- Recommendation: Three extractions, smallest first:
  1. Move `extension CMSampleBuffer` and `extension AVAudioPCMBuffer` (lines 701-774) and `extension NSScreen`/`extension SCDisplay` (345-359) into `Supports/AVBufferConversions.swift`. Pure code move.
  2. Pull `class AudioRecorder` (634-697) into `MicCaptureSession.swift` and rename it for clarity (it conflicts conceptually with `AudioPlayerManager`).
  3. After F-solid-2 lands, split the AppDelegate-extension contents into `CaptureFilterBuilder` (filter logic from `prepRecord` 60-138), `StreamConfigurator` (the `record` body 147-256), `AssetWriterFactory` (`initVideo` + `prepareAudioRecording`), and `FrameDispatcher` (the `stream(_:didOutputSampleBuffer:of:)` callback). The HEIF/PNG snapshot block inside the frame callback (lines 490-543) should be extracted into a `SnapshotExporter` and called via a closure rather than inlined.
- Follow-up plan: refactor: decompose RecordEngine.swift into filter-builder, stream-configurator, writer-factory, and frame-dispatcher

### F-solid-4. QuickRecorderApp.swift is a junk drawer of globals, helpers, extensions, and unrelated value types

- Location: `QuickRecorder/QuickRecorderApp.swift:19-688`
- Severity: High
- Effort:   M
- Status:   confirmed
- Evidence: Beyond `@main struct QuickRecorderApp` (40-95) and `class AppDelegate` (covered in F-solid-2), the file contains: 16 file-scope `let`/`var` globals including six `NSWindow`/`NSPanel` singletons (`mousePointer`, `screenMagnifier`, `camWindow`, `deviceWindow`, `controlPanel`, `countdownPanel`, `previewWindow`, lines 31-37) and `updaterController` (38), plus `fd`, `ud`, `statusBarItem`, `mouseMonitor`, `keyMonitor`, `hideMousePointer`, `hideScreenMagnifier`, `updateTimer`, `scPerm`, `isMacOS12/14/15`; free functions `closeMainWindow`, `closeAllWindow`, `findNSSplitVIew`, `getStatusBarWidth`, `process`, `tips`, `createAlert`, `showAlertSyncOnMainThread` (lines 420-532); extensions on `Bundle`, `String`, `NSMenuItem`, `NSImage`, `utsname` (534-671); a `NNSWindow` subclass and `FixedLengthArray<T>` value type (632-656); and seven domain enums (`AudioQuality`, `AudioFormat`, `VideoFormat`, `PixFormat`, `ColSpace`, `Encoder`, `StreamType`, `BackgroundType`, lines 673-688) that should be model-layer types.
- Why it matters: SRP at file granularity. The "main app entry" file accreted unrelated helpers because there was no obvious other home, which is itself a smell. Anyone adding a new alert helper or a new format enum reflexively appends to this file, deepening the problem.
- Recommendation: Pure code-move PRs, no behavior change:
  1. Move all eight enums (lines 673-688) to `Models/RecordingFormats.swift`.
  2. Move alert helpers `createAlert`, `showAlertSyncOnMainThread`, `tips` to `Supports/Alerts.swift`.
  3. Move `String`/`Bundle`/`NSMenuItem`/`NSImage`/`utsname` extensions to a `Supports/Extensions/` folder, one file per host type.
  4. Move the seven shared `NSWindow`/`NSPanel` globals into a `WindowRegistry` (consumed by the `WindowDirector` proposed in F-solid-2) so they aren't reachable as ambient globals.
  5. Move `FixedLengthArray<T>` to `Supports/FixedLengthArray.swift`.
- Follow-up plan: chore: extract enums, alert helpers, and shared NS extensions out of QuickRecorderApp.swift

### F-solid-5. AudioPlayerManager mixes UI save panel, ObservableObject state, AVAudioEngine plumbing, offline-render export, and post-export MP3 conversion

- Location: `QuickRecorder/ViewModel/QmaPlayer.swift:392-674` (`class AudioPlayerManager`)
- Severity: High
- Effort:   M
- Status:   confirmed
- Evidence: `AudioPlayerManager: ObservableObject` declares 6 `@Published` properties for SwiftUI (393-407), owns three `AVAudioNode`s + an engine (409-412), holds an `NSSavePanel` instance directly (423), and contains `loadAudioFiles`, `play`, `pause`, `stop`, `seek`, `startProgressTimer`, `export`, `saveFile`, `showSavePanel`, `checkBoxToggled`. `saveFile` (561-634) is 73 lines long; it spawns a detached thread, configures offline manual rendering, writes a file, then optionally calls `SCContext.m4a2mp3` and posts a `UNUserNotification` via `SCContext.showNotification`. `showSavePanel` (644-666) constructs an `NSButton` checkbox accessory view and binds `#selector(checkBoxToggled(_:))` (an `@objc` selector on an `ObservableObject` driving SwiftUI) — pure Cocoa UI code embedded in the view-model. The `ObservableObject` is therefore simultaneously a player, an exporter, and a save-dialog controller.
- Why it matters: SRP and DIP. Three independent reasons to change (playback engine, export pipeline, save UI). It also reaches into `SCContext` directly (lines 575, 618, 621, 628, 630), tightly coupling a player view-model to the recording god-object.
- Recommendation:
  1. Extract `QmaAudioPlayer` — pure playback (`play`, `pause`, `stop`, `seek`, progress timer, volume, the three nodes/engine).
  2. Extract `QmaExportService` — the `saveFile` body, taking an injected notification + MP3 converter (decoupling from `SCContext`).
  3. Move `showSavePanel` / `checkBoxToggled` into a SwiftUI-side `QmaExportSheet` view or a small `ExportFilePrompter` helper.
  4. `AudioPlayerManager` becomes a thin coordinator publishing state.
- Follow-up plan: refactor: split AudioPlayerManager into player / export-service / save-panel collaborators

### F-solid-6. AreaSelector view file mixes SwiftUI views, an NSView with hit-testing math, and an NSPanel subclass

- Location: `QuickRecorder/ViewModel/AreaSelector.swift:12-549`
- Severity: Medium
- Effort:   M

### F-solid-7. ContentView reaches into SCContext, AppDelegate.shared, and free closeMainWindow/closeAllWindow throughout

- Location: `QuickRecorder/ViewModel/ContentView.swift:12-256`, with extension at 342-408
- Severity: Medium
- Effort:   S
- Status:   confirmed
- Evidence: The view body calls `SCContext.getMicrophone()` (line 20) on init for `@State`, `SCContext.getSCDisplayWithMouse()` (53, 172, 174), `SCContext.updateAvailableContent` (169), `appDelegate.createCountdownPanel`/`prepRecord` (55-56, 162, 171, 178, 189, 197), `appDelegate.openSettingPanel` (224), `closeMainWindow` and `closeAllWindow` free functions (54, 161, 168, 177, 188, 196, 222), `mouseMonitor = NSEvent.addGlobalMonitorForEvents(...)` directly (173). The view both renders UI and acts as a recording controller. Then the same file extends `AppDelegate` (`showAreaSelector`, `createCountdownPanel`, `createNewWindow` at 343-407), so view-layer code and AppDelegate behavior are co-located.

- Recommendation: Introduce a `RecordingActions` protocol (start audio / start screen / start area / start window / open settings / cancel) and inject it into `ContentView` via `@EnvironmentObject` or initializer. The `AppDelegate` extensions in this file (lines 343-407) belong in the `WindowDirector` proposed in F-solid-2.
- Follow-up plan: refactor: introduce RecordingActions protocol for ContentView (rolls into F-solid-2)

### F-solid-8. SettingsView duplicates @AppStorage keys already declared on AppDelegate

- Location: `QuickRecorder/ViewModel/SettingsView.swift:42-156` (`GeneralView`, `RecorderView`, `OutputView`); compare with `QuickRecorder/QuickRecorderApp.swift:117-148`
- Severity: Medium
- Effort:   S
- Status:   confirmed
- Evidence: `RecorderView` declares `@AppStorage` for `countdown`, `poSafeDelay`, `highlightMouse`, `includeMenuBar`, `hideDesktopFiles`, `trimAfterRecord`, `miniStatusBar`, `hideSelf`, `preventSleep`, `showPreview`, `hideCCenter` (lines 98-108). `OutputView` declares `encoder`, `videoFormat`, `audioFormat`, `audioQuality`, `pixelFormat`, `background`, `remuxAudio`, `enableAEC`, `AECLevel`, `withAlpha`, `saveDirectory` (159-169). All of these are also declared on `AppDelegate` (QuickRecorderApp.swift 117-148). They are kept in sync only because both sides bind to the same `UserDefaults` key string. Renaming a key requires editing both files; missing a rename silently splits the setting in two.
- Why it matters: SRP — settings storage has no single owner. ISP — `AppDelegate` is forced to know every preference even though most of them are only read inside `RecordEngine` and the SwiftUI views.
- Recommendation: Introduce a `RecordingSettings` (`final class: ObservableObject`, or a struct of `@AppStorage`-backed properties exposed via `@EnvironmentObject`) as the single source of truth. `AppDelegate`, `RecordEngine` (after F-solid-2), and every `*View` consume it. Removes ~25 duplicated `@AppStorage` declarations across the two files.
- Follow-up plan: refactor: introduce RecordingSettings observable to replace duplicated @AppStorage keys

### F-solid-9. AVContext mutates SCContext and AppDelegate state instead of returning a session value

- Location: `QuickRecorder/AVContext.swift:13-154`
- Severity: Medium
- Effort:   S
- Status:   confirmed
- Evidence: Both `recordingCamera(with:)` (13-33) and `AVOutputClass.startRecording(with:…)` (62-118) directly assign to `SCContext.captureSession`, `SCContext.previewSession`, `SCContext.filePath`, `SCContext.streamType`, `SCContext.startTime`, and call `closeAllWindow`, `updateStatusBar`, `AppDelegate.shared.startDeviceOverlayer`. `AVOutputClass.fileOutput(_:didFinishRecordingTo:…)` (143-153) hand-rolls a `UNUserNotification` instead of delegating to `SCContext.showNotification`. Two competing notification code paths exist for the same event.
- Why it matters: DIP and SRP. The camera capture path is a small, naturally-cohesive unit but it's wired in via shared mutable globals, so it can't be tested or reused.
- Recommendation: Have `recordingCamera` and `AVOutputClass.startRecording` return a `CameraCaptureSession` value the caller stores. Replace the duplicated notification block (143-153) with a call to the existing `SCContext.showNotification` (or its successor from F-solid-1). Land before/with F-solid-1 because it's small and reduces SCContext's surface.
- Follow-up plan: none — fix inline (small enough to land with F-solid-1's PermissionsCoordinator extraction)

### F-solid-10. String-keyed switch ladders for stream type and format are an OCP smell

- Location: `QuickRecorder/RecordEngine.swift:18-26` (stream type), `:309-316` and `:367-371` (audio/video format), `QuickRecorder/SCContext.swift:190-205` (audio format), `QuickRecorder/SCContext.swift:212-223` (background color)
- Severity: Medium
- Effort:   S
- Status:   confirmed
- Evidence: `prepRecord` (RecordEngine.swift:17) is invoked with `type: String` and immediately switches "window"/"windows"/"display"/"application"/"area"/"audio" into `SCContext.streamType` — even though `enum StreamType` already exists (QuickRecorderApp.swift:685). Every caller passes a string literal (e.g., ContentView.swift:56 `"audio"`, 339 `"display"`, 352 `"window"`, AreaSelector.swift:241 `"area"`). Likewise `updateAudioSettings` (SCContext.swift:186-207) and `prepareAudioRecording` (RecordEngine.swift:309) switch over `AudioFormat.rawValue` strings. `getBackgroundColor` (SCContext.swift:209-225) switches over color name strings rather than the `BackgroundType` enum it uses on the next line.
- Why it matters: OCP. Adding a new stream type requires editing `prepRecord`'s ladder; adding a new audio format requires editing three different switches in two files. Type-safety is also lost — a typo in any caller silently early-returns.
- Recommendation: Change `prepRecord(type:…)` to `prepRecord(type: StreamType, …)` and update the 4-5 callers. For audio format, give `AudioFormat` computed properties (`fileExtension`, `assetWriterSettings`, `avFileType`) and replace the three switches with property reads. Lands as one small PR each.
- Follow-up plan: refactor: replace stringly-typed stream/format switches with enum-driven properties

### F-solid-11. Free top-level globals (mousePointer, camWindow, controlPanel, …) couple every module to UI singletons

- Location: `QuickRecorder/QuickRecorderApp.swift:31-38` (declarations); used in `QuickRecorder/SCContext.swift:336-337,392-396,470,488-490`, `QuickRecorder/RecordEngine.swift:471,485`, `QuickRecorder/AVContext.swift:38,128-129`, `QuickRecorder/ViewModel/AreaSelector.swift:212-216,519-535`, `QuickRecorder/ViewModel/ContentView.swift:173`
- Severity: Medium
- Effort:   M
- Status:   confirmed
- Evidence: Seven `NSWindow`/`NSPanel` instances (`mousePointer`, `screenMagnifier`, `camWindow`, `deviceWindow`, `controlPanel`, `countdownPanel`, `previewWindow`) and three monitors (`mouseMonitor`, `keyMonitor`, `statusBarItem`) are file-scope mutable globals. They are read and written from every layer of the app. Search-and-trace from the use sites cited above shows the same `camWindow` is opened/closed from at least four files.
- Why it matters: DIP and SRP. Any module — RecordEngine, AVContext, view models — can mutate any UI window. There is no single owner of window lifecycle, so window state has to be reasoned about globally.
- Recommendation: Introduce a `WindowRegistry` singleton (or move them into the `WindowDirector` from F-solid-2). Migrate consumers one window at a time. Pairs naturally with F-solid-4 (move out of `QuickRecorderApp.swift`).
- Follow-up plan: refactor: encapsulate floating-window globals behind a WindowRegistry/WindowDirector

## Roll-up

By severity:

- Critical: 2 (F-solid-1, F-solid-2)
- High:     3 (F-solid-3, F-solid-4, F-solid-5)
- Medium:   6 (F-solid-6, F-solid-7, F-solid-8, F-solid-9, F-solid-10, F-solid-11)

Top 3 recommended follow-up plans (severity * 1/effort heuristic):

1. **refactor: split SCContext.swift into capture / state / writer / permissions / post-processing / device-directory collaborators** — F-solid-1. This is the single change that unblocks every other refactor; the god-object's static surface is the dependency target for almost every other finding.
2. **refactor: extract RecordingPipelineCoordinator + MouseAndMagnifierMonitor + WindowDirector from AppDelegate** — F-solid-2. Pairs with #1: once SCContext is decomposed, the AppDelegate extensions become clearly carve-able along the same boundaries.
3. **refactor: replace stringly-typed stream/format switches with enum-driven properties** — F-solid-10. Small, mechanical, high-leverage; lands as a single PR, removes typo-class bugs, and makes the eventual RecordingPipelineCoordinator's API type-safe.

Honourable mentions for cheap early wins: F-solid-4 (code-move out of `QuickRecorderApp.swift`), F-solid-12 (split `QmaPlayer.swift`), F-solid-9 (collapse the duplicate notification path in `AVContext.swift`). All three are sub-day, behavior-preserving, and reduce friction for the bigger plans above.
